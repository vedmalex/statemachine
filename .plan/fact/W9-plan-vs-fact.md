## Смена рамки (директива пользователя)

Все четыре границы упирались в «нельзя/дорого менять ядро». Пользователь снял

## Г2 — I-3 false-positive на КОРРЕКТНОЙ машине (найден и устранён)

Было: промоушен I-3 в DEFAULT обоснован «механизм ISS-030 устранён + корпус
зелёный», живой FP воспроизвести не удалось.

**Найдено (гипотеза fable, подтверждена экспериментом):** FP достижим НЕ по
ISS-030, а по исчерпанию бюджета пампинга. Цепочка `delay:0` invoke-переходов
(каждый hop ≥ QUIET_FLUSH=16 turns, бюджет 1024) при длине ≥40 даёт
`settleReason:'microtask-budget'` → I-3 (в DEFAULT!) объявляет RTC-нарушение.
Машина при этом ДОХОДИТ до финала — то есть корректна.

Измерено: `chain=5,20,35 → ok:true` · `chain=40,60,80,100 → ok:false, I-3`.

**Фикс:** пампер уже считает `fingerprint()` (queue|processing|inFlight) — добавлен
флаг «двигался ли он вообще». При исчерпании бюджета reason расщепляется:
- `progressed` → **`budget-progressing`** (харнесс устал ждать) → I-3 ИСКЛЮЧАЕТ;
- ничего не двигалось → `microtask-budget` (заклиненный дренаж) → ОСТАЁТСЯ witness.

Дискриминатор вычислим из существующих наблюдаемых, НЕ реплицирует семантику
движка (ловушка W5b). Union расширен → bump `header.version` '4'→'5'; корпус-хэши
перебазированы с ПРОВЕРЕННОЙ атрибуцией (откат ТОЛЬКО версии → старая таблица
32/32 ⇒ правка пампера не сдвинула ни бита).

## Г4 — multi-owner: `*For`-семейство

Было: raw-объект 2-м аргументом `fireEvent` неотличим от payload (`args.unshift`),
поэтому мультиобъектный вызов молча резолвился против первичного owner; в W8
добавлена только диагностика.

**Решено:** `fireEventFor(owner, event, ...args)` + `fireEventDetailedFor` +
`canFireEventFor` + `getAvailableEventsFor` — **owner ПЕРВЫМ позиционным**,
неоднозначность устраняется СТРУКТУРНО (слот 1 = owner, слоты 3+ = аргументы), а не
duck-check'ом. Raw-объект принимается и нормализуется через WeakMap-кэш; per-owner
карты ключуются по adaptee, поэтому объект сохраняет свои таймеры/инвоки/историю.
`fireEvent` НЕ тронут (трактовать raw как owner = API-аналог false-positive: сломало
бы легитимный payload с полем `stateAttribute`).

Попутно (находка fable): `canFireEvent` типизирован как принимающий Adapter, но
runtime-проверки не было — raw-объект пролезал и читался как адаптер, молча выдавая
мусор. Теперь нормализуется.

## Г1 — I-5 получил РЕАЛЬНЫЕ зубы

Было: невозможно отличить «raise не было» от «raise был, не совпал ни с одним
кандидатом» (при `rejected.length===0` селекция не пишет ничего).

**Решено:** `raiseEvent` (ЕДИНАЯ приватная точка, 5 call-site) получил ОБЯЗАТЕЛЬНЫЙ
параметр `origin` — TypeScript ломает компиляцию на каждом вызове, поэтому будущий
шестой не сможет «забыть». Эмитит `kind:'raise'` (смежная пара begin+end, `edge` не
расширен).

Предикат I-5 — **счётный**, `scope:'final'`: `edges(C) > raises(C)`, где edges =
переходы `doneDelta[C]` false→true на соседних boundary-фреймах (шаги с любым
`synthetic` исключены), raises = записи `kind:'raise'` с нужным `event`. Он ВООБЩЕ
не спрашивает «была ли enabled-транзиция» — то есть не реплицирует селекцию.
Направление `>` безопасно: расхождения гранулярности дают `raises >= edges`.

Planted-defect БЕЗ мутации движка: монитор, глотающий raise-записи → I-5 стреляет;
без фильтра — чисто. I-5 в DEFAULT; **`DOCUMENTED_NO_OPS` теперь ПУСТ** — честных
no-op-оракулов не осталось.

Честно запиннено ограничение: join, который ПОКИДАЕТ композит, моргает done→left
внутри одного макрошага, boundary не видит `done:true` → I-5 корректно вакуумен
(безопасная сторона), и это отдельный тест.

## Движковый фикс — join после errorState-recovery (найден через Г1)

Строя предикат I-5, агент упёрся в асимметрию: успешный коммит зовёт
`checkCompletion`, а errorState-коммит — нет. Он не стал «исключать это как FP
оракула», а вынес вопрос к движку.

**Проверено — реальный дефект ДВИЖКА:** recovery в all-final конфигурацию давала
`isDone(C)===true` при НЕподнятом `done.state.<C>` → обработчик завершения молча не
срабатывал. Репро: композит с r2 уже final, ошибка в r1 → `errorState:'P.r1.done'`
→ конфигурация all-final → join потерян.

**Фикс:** `checkCompletion` вызывается и на errorState-пути. Формулировка:
*завершённость — свойство закоммиченной конфигурации, а не способа, которым в неё
попали*. Recovery остаётся recovery (успех не записывается, `fired:false` цел).
Второй тест пиннит edge-triggered семантику (неполное восстановление → join нет).

## Г3 — minimalTrace/shrink: все три структурные причины сняты

| причина | как снята |
|---|---|
| разные входы (live config vs ScenarioSpec) | ddmin идёт по ПОТОКУ ОП'ОВ; кандидат — ТОТ ЖЕ живой конфиг с теми же замыканиями. `SimOptions.script` + `SimResult.ops` |
| нет предиката для user-violation | строгий кортеж `{invariant, witness}`; builtin — существующий `fingerprint` через ТОТ ЖЕ `fingerprintEquals` (предикаты не могут разойтись) |
| payload не сериализуем | сериализация нужна только чтобы НАПЕЧАТАТЬ репро, не чтобы шринковать: args живут в памяти как непрозрачные значения |

Анти-фабрикация: verify-first (не воспроизвелось → `shrink-skipped`, никогда
неверифицированный minimal); мемо-ключ по ИНДЕКСАМ исходного потока.

**Ошибка, найденная и исправленная по ходу (оркестратор):** первая версия ключа
использовала содержимое (`event`-имена) — и payload-генератор, выдающий РАЗНЫЕ args
для разных вызовов ОДНОГО события, схлопывал два разных кандидата в один ключ.
Репро: предикат вызывался 1 раз вместо 3, валидное сокращение терялось. Это тот же
класс, что `[object Object]` в `shrinkCacheKey`. Исправлено на индексную
идентичность + 2 регресс-теста.

**Ошибка, найденная агентом:** `structuredClone` не бросает на инстансе класса, а
молча срезает прототип → `instanceof`-гарды падали → реплей расходился → находка
терялась ИЗ-ЗА САМОЙ МЕРЫ БЕЗОПАСНОСТИ. Клонирование теперь гейтится
`argsArePlainData`; не-plain args идут по ссылке с пометкой `non-serializable`.

Реальный результат: поток из 40 op'ов сведён к 1 за 10 прогонов, репро —
исполняемый сниппет со `script`.

## W9.1 — приёмка критика нашла ДЕФЕКТ В МОЁМ ЖЕ ФИКСЕ Г2

Критик (и независимо доксинк-агент) вскрыл, что флаг `progressed` **липкий на весь
settle**: `prev = fingerprint()` берётся до первого turn'а, когда fired-событие уже
в очереди, поэтому первый же turn его взводит, а сброса нет. Следствие: любой settle,
инициированный `fire`, помечен progressed навсегда → «поработал, потом заклинил»
классифицируется как `budget-progressing`, I-3 молчит. **Я обменял ложное
срабатывание на молчание, а не на честный сигнал** — ровно тот класс ошибки, который
сам ищу в чужом коде.

**Фикс:** липкий boolean → `lastMoveTurn` + окно `PROGRESS_RECENCY_WINDOW = 4 ×
QUIET_FLUSH`. Обоснование границы ИЗМЕРЕНО, не предположено: максимальный тихий
разрыв на корректных фикстурах (цепочки 5/20/40/60/120 hop) — **16 turn'ов** (ровно
QUIET_FLUSH, структурная граница пампера), в точке исчерпания — 9–11; у заклиненной
машины — **1007**. Окно 64 = 4× запас сверху и ~16× снизу.

Ключевой аргумент звуковости: `budget-progressing` ⊂ «двигался хоть раз» ⊂ множество,
которое ДО-фикс код целиком звал `microtask-budget`. Значит I-3 может срабатывать
только РЕЖЕ, чем в до-фиксном коде, проверенном на корпусе нулевых ложняков —
и никогда чаще. Расширение окна может только ещё сильнее заглушить I-3, но не
обвинить корректную машину.

**Оживлена мёртвая проводка:** `LivenessParams.microtaskBudgetExhausted` объявлен и
потребляется в `analyzeLiveness`, но продюсера НЕ БЫЛО ни одного (только тест его
ставил) — заклиненный дренаж вообще не доходил до liveness-вердикта. Теперь питается
из кадров с `settleReason === 'microtask-budget'` и НИКОГДА из `'budget-progressing'`
(иначе вернулся бы ровно тот ложняк, ради которого всё делалось).

**`budget-progressing` → advisory-warning** (один на прогон, `count` = кратность),
`ok` не трогает; сообщение указывает на `steps` как на реальную ручку — агент
проверил эмпирически (`chain200`: steps=1 → h36, 2 → h108, 3 → h180, 6 → h200), а
публичного `maxTurns` в API нет, и он честно отказался писать неверный совет.

**Тесты с зубами** (`budget_wedge.test.ts`, 8 штук на РЕАЛЬНЫХ машинах, без моков):
против дефектного кода падают 5 — я перепроверил это независимо, замутировав
классификатор в липкое поведение: **4 из 8 падают**, после восстановления — все зелёные.

## Delay-0 livelock — честная граница (разбор fable)

Вопрос: можно ли вернуть ВЕРДИКТ для `A ⇄ B` на delay-0? Ответ: **нет**, и это
доказано, а не признано за неимением идей. Оба соблазнительных пути опровергнуты
конкретными КОРРЕКТНЫМИ машинами:

1. та же топология со счётчиком-гардом, выходящим после N итераций за горизонтом
   бюджета, даёт **побайтово тот же префикс** на всех каналах;
2. корректная цепочка через общий hub даёт повтор конфигурации на границе
   (у сэмпла `pendingTimers`/`earliestTimerAt` захардкожены, отпечаток вырождается
   в `(config, queueDepth)`).

Различающее состояние — поля контекста и переменные замыканий — не наблюдаемо ни в
одном канале: у `TraceFrame` нет поля контекста, записи жизненного цикла намеренно
без payload'ов. Решать «остановится ли это» из конечного префикса = решать
остановку произвольного пользовательского кода по данным, которые его не определяют.
Warning-only здесь — не компромисс, а звуковой максимум; граница записана в
`docs/dynamic-check.md`.

Попутно закрыты: ложный блок «KNOWN RESIDUAL — errorState fallback» в I-5 (резидуал
закрыт движковым фиксом этой же волны), цепочка версий '4'→'5' в комментариях
`driver.ts`/`public.ts`, JSDoc-оговорка про слабый duck-тест `isAdapter` на новой
публичной поверхности `*For`.
