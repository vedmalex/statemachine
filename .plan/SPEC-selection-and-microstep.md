## Решения владельца (зафиксированы, не переоткрывать без явной отмены)

1. **`priority` — override выше всего**, значение по умолчанию **`0`** (не `-Infinity`).
2. **Optimal transition set реализуется**: за одно событие может сработать несколько
   непротиворечивых переходов в разных регионах.
3. **Объём релиза максимальный**: селекция + OTS + единый компилятор конфига + F7 + F8 + F10 +
   документация и migration-note.

## 1. Нормализованная модель конфига (compile-pass)

Причина: сегодня понятие «валидный путь» реализовано трижды — в `config_validator.ts`, в рантайме
(`updateState` / `isTransitionPossible` / `validateCompositeState`) и в README. F10 — симптом этого,
а не отдельный баг. Плюс порядок `|`-листов сейчас map-insertion-зависим (признано в
`state_machine.ts:1478-1483`), а OTS без детерминированного document order недетерминирован.

Конфиг компилируется **один раз** в конструкторе в модель:

```ts
type NodeKind = 'leaf' | 'composite' | 'region'

interface ModelNode {
  id: string            // полный путь: 'P', 'P.gate', 'P.gate.DA_PENDING'
  kind: NodeKind
  parent: string | null
  depth: number         // корень = 0
  documentIndex: number // глобальный порядковый номер обхода конфига — ЕДИНСТВЕННЫЙ источник document order
  isFinal: boolean
  children: string[]    // в порядке объявления
}
```

- Обход — в порядке `Object.keys` конфига, рекурсивно: состояния, затем их регионы, затем состояния
  регионов. `documentIndex` присваивается на входе в узел.
- Регион — самостоятельный узел (`kind: 'region'`), его `id` = `<композит>.<имя региона>`. Это
  снимает нынешнюю неразличимость «лист `a.b`» и «регион-контейнер» (следствие `getRegionKey`,
  `state_machine.ts:2435-2441`).
- Модель — единственный вход для валидатора и рантайма. Строковое представление конфигурации
  (`'a.r.x|b.q.y'`) остаётся **только** на границе персистенции и в публичном API.

Валидатор после этого проверяет модель, а не парсит пути заново. F10 (`INVALID_INITIAL_STATE` на
точечном `initial`) исчезает как класс: `initial` резолвится тем же кодом, что и рантайм.

## 1а. Статическая проверка модели

Валидатор перестаёт быть отдельным парсером и становится набором проверок **над моделью** — то же
дерево, что интерпретирует рантайм. Сегодня у него 38 диагностических кодов, но проверки, связанные
с вложенностью, либо врут, либо отсутствуют.

**Чинится (существует, но сломано на регионах):**

| код | что не так сейчас |
|---|---|
| `UNREACHABLE_STATE` | ложно-положителен на всех вложенных: на README-примере объявляет недостижимыми `proc.a.run` / `proc.b.run` — входные листья регионов. Переделать на обход достижимости от начальной конфигурации по переходам с учётом композитов, регионов и точечных путей. |
| `INVALID_INITIAL_STATE` | F10: не понимает точечный `initial`. |
| `REGION_MISSING_INITIAL` | сообщение про insertion-order останется полезным ровно до тех пор, пока `initial` нельзя пинить; после фикса F10 — понизить до info. |

**Новое — корректность конфигурации:**

| код | severity | что ловит |
|---|---|---|
| `REGION_STARTS_FINAL` | error | входное состояние региона помечено `final` → join смыкается немедленно, работа не начинается. Сегодня не ловится; потребитель закрывал это ручным контрактным тестом. |
| `REGION_NO_PATH_TO_FINAL` | error | из входного состояния региона **нет пути** к `final`. Существующий `REGION_NO_REACHABLE_FINAL` проверяет лишь НАЛИЧИЕ финального листа, а не достижимость пути к нему. |
| `UNSATISFIABLE_FROM` | error | составной `from` называет два состояния одного региона (`'P.a.x\|P.a.y'`) — не выполним никогда. |
| `DEAD_END_STATE` | warning | нет исходящих переходов, не `final` и не корневое терминальное — тупик. |
| `DUPLICATE_REGION_NAME` | error | коллизия имён областей в одном узле (нужно и для будущего `composeIntoRegion`). |
| `INVOKE_NO_HANDLER` | warning | новая форма `invoke` со `src`, но без `onDone` и `onError` — результат операции теряется молча. |

**Новое — следствия новой семантики селекции:**

| код | severity | что ловит |
|---|---|---|
| `ANCESTOR_DESCENDANT_OVERLAP` | warning | на одном событии есть переходы от предка и от потомка → победит потомок; если задумано обратное, нужен `priority` на родительском. Прямо адресует случай «аварийный выход из композита». |
| `PRIORITY_INVERTS_DOMINANCE` | warning | `priority` предка выше, чем у потомка — осознанная инверсия стандартного правила. Заменяет нынешний `MIXED_PRIORITIES`, который после `default = 0` теряет смысл. |
| `CROSS_REGION_CONFLICT` | warning | переходы из разных регионов на одно событие с пересекающимися exit-set → сработает один, второй регион не отреагирует (§6.2). |
| `WILDCARD_SHADOWED` | info | `from: '*'` соседствует с явными путями и всегда проигрывает им. |

**Политика применения (уточнена в W2b по факту рантайм-совместимости).** Разделены два класса
model-ошибок:
- **Бросают при конструкции** — только `INVALID_STATE_PATH` (битый/несуществующий путь `from`/`to`):
  генуинно-непостроимый случай, рантайм на нём и так бросает. `createMachine`/`new StateMachine`
  теперь прогоняют валидацию и бросают `StateMachineError` (было: логировали и строили сломанную
  машину — V6).
- **Репорт-ошибки** (`isValid:false`, `validateConfigStrict` поднимает до throw, доступны
  программно, НО НЕ бросают при обычной конструкции) — `REGION_STARTS_FINAL`,
  `REGION_NO_PATH_TO_FINAL`, `UNSATISFIABLE_FROM`, `DUPLICATE_REGION_NAME`. Причина: рантайм
  СОЗНАТЕЛЬНО исполняет эти вырожденные-но-исполнимые конфиги (композит с единственным
  final-листом — `regions:{r:{f:{final:true}}}` — легитимен в замороженных suite runtime_stability/
  reentrancy_precision и в D12 all-final join). Бросок снёс бы протестированное поведение и реоткрыл
  бы гейты. `validateConfigStrict` даёт потребителю строгий режим, когда он хочет отвергать и их.

Warning'и остаются советующими; `info` (напр. `WILDCARD_SHADOWED`) — в отдельном `result.infos[]`.

## 1б. Доставка валидатора — три уровня (все три, не по отдельности)

Один и тот же движок проверок (§1а над моделью), выставленный тремя способами. Решение владельца:
делать **все три сразу** — оставленное «на потом» не возвращается. Отдельного линтера-анализатора
исходников НЕ делаем: конфиги генерируются функциями (`createGatedPhaseSmConfig(tier)`), их не видно
статически — проверять надо скомпилированную модель, а не текст.

1. **Бросок при компиляции конфига.** Ошибки модели (§1а) бросают в конструкторе `StateMachine` /
   `createMachine`. Ловит и генерируемые конфиги в момент создания машины. Основной контур. Сегодня
   `createMachine` только логирует «validation failed» и строит сломанную машину (V6).
2. **`validateConfig(config)` как экспорт.** Уже используется потребителем
   (`validateGatedPhaseSmForTier`). После переделки на модель начнёт давать правду. Критерий
   приёмки: на конфигах MB3 остаются только НАСТОЯЩИЕ предупреждения (сегодня 28, из них
   большинство — ложные `UNREACHABLE_STATE` и следствия F10).
3. **Тонкий CLI + отчёт о машине.** `statemachine lint <модуль> --export <fn> --args <...>`:
   импортирует модуль, вызывает фабрику, компилирует модель, печатает диагностику. Плюс
   человекочитаемый отчёт из побочного продукта модели: граф достижимости, тупики, для каждого
   региона путь до `final`, мёртвые события (ни одного достижимого `from`). Ценность — проверка
   перестаёт зависеть от того, написал ли потребитель тест; на 23 конфигах в голове не удержать.

Все три — тонкие обёртки над §1а, не три разных реализации.

**Динамическая проверка (§13) — четвёртый уровень, поставляется потребителю.** Не «опциональный
хвост»: решение владельца — сделать полноценно, отдать потребителям как инструмент тестирования их
машин и задокументировать. Строится НАДСТРОЙКОЙ над существующим `src/sim`, не с нуля.

## 2. Активная конфигурация

Множество активных **атомарных листьев**, упорядоченное по `documentIndex`. Порядок больше не
зависит от вставки в `Map`.

## 3. Кандидаты и `matchedSources`

Кандидат — переход события `E`, чей `from` удовлетворён активной конфигурацией. При матчинге
фиксируется **`matchedSources`**: по каждой части `from` — конкретный активный узел (лист или его
предок), которым эта часть удовлетворена. Без этого сравнение «кто глубже» неопределимо.

## 4. Правило упорядочивания

Кандидаты упорядочиваются **до** исполнения гардов:

1. **`priority`** по убыванию, `default = 0`.
2. **Класс специфичности источника**: `0` — полностью явный `from`; `1` — частичный wildcard
   (`'a|*'`); `2` — полный `from: '*'`. Меньше = приоритетнее.
3. **Доминирование потомка** (pointwise, НЕ численная глубина): `T1` доминирует `T2`, если по
   каждой сопоставленной части источник `T1` равен или является потомком соответствующего источника
   `T2`, и хотя бы по одной — строгим потомком.
4. **Document order** — первый объявленный побеждает.

**Реализационная тонкость (обязательна).** Доминирование — **частичный** порядок. Использовать его
как ветку компаратора нельзя: компаратор перестанет быть транзитивным и сортировка станет
нестабильной. Порядок применения:

- отсортировать стабильно по `(priority ↓, специфичность ↑, documentIndex ↑)`;
- затем **отфильтровать**: удалить `T2`, если существует `T1` с тем же `priority` и той же
  специфичностью, строго доминирующий `T2`.

Несравнимые источники (разные регионы, разные ветви) доминированием **не** ранжируются — они
расходятся на шаге 4. Это соответствует UML (приоритет определён только вдоль цепочки
предок–потомок) и SCXML (подъём от листа вверх), и отличается от численной глубины, которая давала
бы ложные победы между ветвями.

## 5. Гарды — лениво

- Гарды исполняются **в порядке из §4**, до первого прошедшего. Гарды оставшихся кандидатов **не
  исполняются**.
- Исключение внутри гарда: переход считается disabled, вызывается `monitor.recordError`, причина
  сохраняется как `guard-error` (закрывает **F7**).
- Гард победителя **не перепроверяется** при применении: Phase 1 в `applyTransition`
  (`state_machine.ts:1949-1963`) сносится (закрывает **F8**). Обязателен тест-счётчик вызовов —
  сегодня количество вызовов не зафиксировано ни одним тестом.

Наблюдаемое следствие: множество исполняемых гардов меняется. Для нечистых гардов это видимое
изменение поведения — в migration-note.

## 6. Микрошаг: optimal transition set

### 6.1 Выбор

```
enabled = []
claimed = ∅                       // листья, уже обслуженные выбранным переходом
for leaf of activeLeaves (по documentIndex):
    if leaf ∈ claimed: continue
    for node of [leaf, ...ancestors(leaf)]:      // снизу вверх
        cand = кандидаты, у которых matchedSource для этого листа == node, в порядке §4
        t = первый из cand, чей гард прошёл (гарды лениво, §5)
        if t: enabled.push(t); claimed ∪= листья, покрытые t; break
```

Подъём снизу вверх даёт приоритет потомка «бесплатно» — так же, как в SCXML.

### 6.2 Снятие конфликтов

Два перехода конфликтуют, если их **exit-set** пересекаются. `exitSet(t)` — активные узлы поддерева
LCCA(`matchedSources(t)`, `to`), подлежащие выходу.

```
filtered = []
for t1 of enabled (в порядке добавления):
    if ∃ t2 ∈ filtered: exitSet(t1) ∩ exitSet(t2) ≠ ∅:
        if source(t1) — строгий потомок source(t2): заменить t2 на t1   // preempt потомком
        else: отбросить t1                                              // выигрывает более ранний лист
    else: filtered.push(t1)
```

### 6.3 Исполнение

1. Объединённый exit-set, порядок **descendant-first**: `depth ↓`, при равной глубине
   `documentIndex ↑`.
2. `onExit` по каждому узлу; per-leaf таймеры `invoke` гасятся при выходе листа (как сейчас).
3. История.
4. `onTransition` каждого сработавшего перехода — в порядке `filtered`.
5. Объединённый enter-set, порядок **ancestor-first**: `depth ↑`, при равной глубине
   `documentIndex ↑`.
6. `onEnter`.
7. Обновление конфигурации — одной операцией по всем переходам сразу (нынешний `updateState`,
   `state_machine.ts:2314-2355`, обобщается на список целей).
8. `done.state.<id>` для композитов, ставших полностью финальными, — innermost-first (существующая
   логика `checkCompletion` сохраняется, но её сортировка по строковой глубине заменяется на
   `depth` из модели).

## 6а. Прерывание лэйнов и отмена операций

Сценарий: композит с регионами-«лэйнами», каждый лэйн — реальная операция (чтение, запись).
Нужно, чтобы лэйны узнавали об аборте и **сворачивали свою работу**, а не только меняли состояние.

**Что уже работает и сохраняется.** Выход из композита проводит `onExit` по всем активным
вложенным листьям descendant-first, и payload события прокидывается в обработчики:
`fireEvent('ABORT', {cause})` → `read.busy.exit({cause})` → `write.busy.exit({cause})` →
`RUN.exit({cause})`. Нормальное завершение через join безопасно по построению: `done.state.<P>`
поднимается только когда **все** регионы финальны, поэтому родитель не может выйти раньше лэйнов.

**Что чинится OTS.** Сегодня ABORT, объявленный в каждом лэйне, срабатывает **только в одном**
(последнем объявленном) — второй лэйн остаётся в рабочем состоянии и про аборт не узнаёт.
Замер: `[{from:'RUN.read.busy'…},{from:'RUN.write.busy'…}]` → `RUN.read.busy|RUN.write.done`.
После OTS срабатывают оба. Это основной способ «каждый лэйн сам себя сворачивает».

**Что требует явного `priority`.** Если ABORT объявлен и у родителя, и в лэйне, после смены правила
победит лист и выхода из композита не произойдёт. Аварийный выход пишется как
`{ from: 'RUN', to: 'ABORTED', priority: 1 }`.

**Пробел, который надо закрыть.** `invoke` — это только таймер (`{ delay, event, cond?, action? }`);
понятия «длительная операция, привязанная к состоянию, с отменой» в библиотеке нет. При выходе из
листа гасятся его таймеры, но промис, запущенный вручную в `onEnter`, продолжает выполняться и
может записать результат уже после аборта. Кроме того, `onExit` не знает причину выхода
структурно — только payload события.

**Решения владельца (зафиксированы 2026-07-28):**

**(а) `invoke` расширяется до полноценной операции** с автоматической отменой при выходе из листа —
модель SCXML `<invoke>` + `cancel`. Существующая таймерная форма сохраняется как отдельный вариант,
чтобы не ломать текущие конфиги:

```ts
type StateInvocation<T> =
  // существующая форма — таймер (сохраняется)
  | { delay: number; event: EventName; cond?: (a: T) => boolean; action?: ActionOrString<T> }
  // новая форма — длительная операция
  | { src: (adaptee: T, signal: AbortSignal, ...args: any[]) => Promise<unknown>
      onDone?: EventName          // событие при успешном завершении; результат уходит в payload
      onError?: EventName         // событие при отказе; ошибка уходит в payload
      cond?: (a: T) => boolean
      id?: string }               // для диагностики и адресной отмены
```

Правила:
- операция запускается при входе в лист (после `onEnter`), её `AbortController` живёт вместе с
  листом рядом с per-leaf таймерами (`activeTimers`);
- при выходе из листа — `abort()` **до** `onExit`, чтобы обработчик выхода видел уже отменённую
  операцию; отмена синхронная, ожидание завершения промиса не блокирует переход;
- `onDone` / `onError` поднимаются как внутренние события через ту же очередь; событие от
  **отменённой** операции игнорируется (лист уже покинут) и не попадает в очередь;
- отказ операции без объявленного `onError` — `monitor.recordError`, не молчаливое проглатывание
  (та же политика, что для гардов в §5);
- под DST операция обязана быть детерминируемой: запуск и отмена проходят через инжектированный
  scheduler, как и таймеры.

**(б) `ExitContext` добавляется ДОПОЛНИТЕЛЬНЫМ аргументом** (не заменяет payload события —
существующие обработчики продолжают работать, просто игнорируют лишний аргумент):

```ts
interface ExitContext {
  event: string            // событие, вызвавшее выход
  preempted: boolean       // true — свернули извне; false — регион дошёл до final
  wasFinal: boolean        // был ли покидаемый узел final на момент выхода
  target: string           // целевая конфигурация перехода
}
// onExit(adaptee, ...payloadСобытия, exitContext)
```

Лэйн теперь отвечает на вопрос «меня свернули или я закончил» структурно, без косвенных признаков.

## 7. Публичные контракты

| метод | поведение |
|---|---|
| `fireEvent(...)` | `Promise<boolean>` — `true`, если сработал **хотя бы один** переход. Бросок при отсутствии кандидатов сохраняется (обратная совместимость). |
| `fireEventDetailed(...)` | `Promise<FireResult>` — **не бросает**, отсутствие кандидатов возвращается как `reason: 'no-transition'`. |
| `canFireEvent(...)` | без изменений: формальная проверка без гардов. JSDoc-строка «guards are not executed» переносится в README, называется сценарий применения (меню действий). |

```ts
type FireResult =
  | { fired: true
      transitions: Array<{ event: string; from: string; to: string }> }  // все сработавшие
  | { fired: false
      reason: 'no-transition' | 'guard-rejected' | 'guard-error'
      rejected?: Array<{ transition: string           // 'A -> B'
                         reason: 'guard-rejected' | 'guard-error'
                         error?: Error }> }
```

Возврат `fireEvent` **не меняется**: `{ fired: false }` — truthy объект, любой
`if (await sm.fireEvent(e))` молча инвертировался бы, и TypeScript этого не поймал бы.

## 9. Миграция (потребитель MB3)

1. **Аварийный выход из композита** по событию, объявленный как `from: '<P>'`, после смены правила
   проигрывает любому внутрирегиональному обработчику того же события. Выражается явно:
   `{ from: 'P', to: 'ABORT', priority: 1 }`.
2. Контрактный тест на порядок ключей регионов (обход F10) теряет смысл: `documentIndex`
   детерминирован, а `initial` снова можно пинить явно.
3. Гарды с побочными эффектами увидят другое число вызовов: победитель — один раз вместо двух,
   проигравшие могут не вызваться вовсе.
4. Событие, обрабатываемое в двух регионах, теперь сработает **в обоих**. Это самое заметное
   изменение: раньше второй регион молча терял реакцию.

## 10. Тест-план (минимум, до реализации)

Селекция: `priority` default 0 (отрицательный больше не бьёт неуказанный); специфичность
явный > `'a|*'` > `'*'`; доминирование потомка при любом порядке объявления; несравнимые источники →
первый объявленный; ленивость (счётчик вызовов гардов: победитель ровно 1, проигравшие 0).

OTS: два региона реагируют на одно событие → оба перехода сработали; конфликтующие exit-set →
преемпция потомком; порядок exit descendant-first и enter ancestor-first при нескольких переходах;
`done.state` после микрошага, а не в его середине.

Лэйны и отмена: ABORT в каждом лэйне → сработали ВСЕ (сегодня только последний объявленный);
ABORT у родителя с `priority` побеждает листовой; `abort()` вызван до `onExit` и `signal.aborted`
виден в обработчике; событие `onDone` отменённой операции НЕ попадает в очередь; операция без
`onError`, завершившаяся отказом, попала в `monitor.recordError`; `ExitContext.preempted` = `true`
при аборте и `false` при нормальном join; отсутствие утечки `AbortController` после выхода.

Регрессии: F7 (ошибка гарда → `guard-error` + `recordError`), F8 (ровно один вызов гарда),
F9 (все четыре случая из находки), F10 (`validateConfig` принимает точечный `initial`, включая
`'a.r|b.q'`, и канонический пример README проходит целиком).

## 11. Открытые вопросы — статус

- **[РЕШЕНО]** Multi-part `from: 'a|b'` и частичный `'a|*'`: **сохраняются** с pointwise-доминированием
  (§4). Не deprecated — гарды не покрывают AND-источник из нескольких регионов.
- **[РЕШЕНО]** Кросс-региональный конфликт при пересекающихся exit-set: **порядок листьев**
  (document order, §6.2). Не «ambiguous transition»-ошибка — детерминизм важнее строгости для
  единственного потребителя.
- **[ГЕЙТ W3, владелец — первый шаг W3]** `transitionTimeout` при нескольких переходах за микрошаг:
  один дедлайн на микрошаг vs на переход. РЕШИТЬ до реализации OTS (MASTER §3/§7). Рекомендация к
  решению: **один дедлайн на микрошаг** — микрошаг атомарен по семантике RTC, поэтапный дедлайн на
  переход противоречил бы «все переходы применяются как одно целое».

## 13. Динамическая проверка конфига потребителя (поставляемая фича)

Цель: потребитель отдаёт СВОЮ машину и получает отчёт о том, что статика доказать не может, потому
что не видит гардов — фактически недостижимые состояния, дедлоки, регионы, не сходящиеся к `final`,
непокрытые переходы, нарушения его собственных инвариантов.

**Фундамент уже есть в `src/sim`** — строим фасад, а не движок:

- `runSimulation(setup, opts)` (`src/sim/public.ts:626`) уже принимает `SimTarget = { config, owner }`
  — то есть КОНКРЕТНУЮ машину потребителя, не только генерированную топологию.
- `coverage.ts` уже собирает покрытие состояний (`visitState`, `uncovered > 0` → провал).
- Инварианты `safety`/`liveness` (`invariants.ts`, `liveness.ts`), `fairness.ts`, `faults.ts`,
  `shrinker.ts` (минимизация контрпримера), `repro-codegen.ts` (кодоген воспроизведения),
  виртуальные `clock`/`scheduler` — всё готово.
- Существующий аппарат заточен под ВНУТРЕННИЙ DST (генерирует случайные машины, проверяет инварианты
  ДВИЖКА). Потребителю нужен обратный режим: фиксированная машина, перебор/фаззинг СОБЫТИЙ.

**Что делаем — потребительский фасад:**

```ts
import { checkMachine } from '@vedmalex/statemachine/sim'

const report = await checkMachine(config, owner, {
  events: ['GO', 'ABORT', ...],   // алфавит; по умолчанию — все из конфига
  seed: 'ci-1',                    // детерминированно воспроизводимо
  steps: 10_000,
  invariants: [                    // опционально — свойства потребителя
    { name: 'no-orphan-lane', check: (s) => ... },
  ],
})
// report: { reachableStates, unreachableStates, deadlocks, nonConvergingRegions,
//           uncoveredTransitions, deadEvents, violations: [{ invariant, minimalTrace }] }
```

- перебор событий поверх виртуального времени (`scheduler`/`clock` из `SimEnv`) — детерминизм и
  воспроизведение по `seed`;
- **гарды исполняются реально** — в этом всё отличие от §1а: путь, статически «достижимый», может
  быть недостижим при фактических гардах, и наоборот;
- контрпример минимизируется `shrinker`'ом и выдаётся как воспроводимый код (`repro-codegen`);
- отчёт — тот же побочный продукт, что у CLI (§1б), плюс динамические факты (что реально посещено).

### 13.3 Что sim НЕ гарантирует (обязательно в документации фасада)

Прямо из непокрытого аудитом — фасад обязан честно назвать границы: глубокая иерархия, приоритеты,
вложенные композиты, `transitionTimeout`, >2 регионов внутренним генератором не порождаются (но путь
машины потребителя от этого не страдает — он идёт мимо генератора); порядок входа/выхода иерархии не
проверяется (I-4 мёртв); отсутствие обязательного `done.state` не ловится (I-5 мёртв); молчаливое
превышение queue-bound (I-9). Это фаззинг, не model-checking: отсутствие нарушения ≠ доказательство.

**Документация (обязательная часть фичи):** раздел в README/docs — что проверяет, чего НЕ может
(свойства зависят от полноты алфавита событий и инвариантов; отсутствие нарушения ≠ доказательство
корректности, это фаззинг, а не model-checking), как читать отчёт, как воспроизвести контрпример,
как писать свои инварианты. Без честной границы «что гарантирует / что нет» инструмент введёт в
заблуждение сильнее, чем его отсутствие.

*Цена:* фасад + отчёт — дни; аудит `sim` — отдельно и заранее; документация — обязательна.
*Порядок:* после компилятора модели (§1) и стабилизации семантики — иначе фасад придётся
переписывать под каждое изменение движка.
