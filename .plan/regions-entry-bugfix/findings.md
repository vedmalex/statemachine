**Additional findings:**

- _[high]_ SCXML-correct semantics for case (a) — a transition whose source is a composite/parallel parent while leaf states are active: in SCXML a transition is selected if its source state is in the active configuration (the set of all active states including ALL ancestors of active atomic states). When 'council.regionA.aRun' is active, ancestors 'council.regionA', 'council', and the root are ALL in the active configuration. Therefore from:'council' SHOULD match in the expanded state. The current code's per-region-key Map cannot express this because it only stores the deepest leaf per region key and never materializes ancestor membership. — SCXML spec: active configuration = atomic states + all their proper ancestors (incl. parallel and compound parents). Current parseCompositeState (sm.ts:2022-2034) stores only leaf-per-regionKey, no ancestors.
- _[high]_ SCXML-correct semantics for case (b) — JOIN firing: SCXML has no 'join' primitive; the equivalent is a transition out of a <parallel> state. Such a transition is eligible whenever the parallel parent is active (i.e. ALWAYS while any region is active) — it is NOT gated on all regions reaching a final state. To express 'fire only when ALL regions reach final' (true UML join / ANY-vs-ALL), SCXML uses the <final> child per region plus the auto-generated done.state.<id> event, or an explicit guard checking In(regionA.final) && In(regionB.final). The engine today has NO ALL-regions-final gating and no In()/done.state mechanism; from:'parent' would fire on ANY active leaf, which is the parallel-exit (ANY) semantics, not a true ALL-join. — No 'final'/'done.state'/'In(' handling found in state_machine.ts. isTransitionPossible matches per-from with .every() over '|'-split from parts (sm.ts:1547-1561) — that is ALL across explicitly listed from-parts, but a single bare 'parent' from is one part, giving ANY-leaf semantics.
- _[info]_ EXACT change set to support composite-parent 'from' matching WITHOUT breaking simple-state matching: the matching predicate must test ANCESTOR membership against the active configuration, not exact region-key equality. Minimal approach: in isTransitionPossible, replace the regionKey lookup (sm.ts:1553-1560) with: for each fromState, return true if ANY active leaf L in currentStates.values() satisfies L===fromState || isParentState(fromState, L) (i.e. fromState is an ancestor of, or equal to, an active leaf). isParentState already implements the ancestor test but is currently called with arguments SWAPPED for this purpose — here we need isParentState(parentState=fromState, childState=L). This single change makes from:'council' match the expanded config AND continues to match exact leaves (L===fromState) and the existing from:'p.region' case (ancestor of leaf). getRegionKey would no longer gate join matching (it stays for parseCompositeState/updateState region bookkeeping). — isParentState sm.ts:1564-1568 (ancestor test exists); current call site sm.ts:1559 passes (current, from); proposed call passes (from, leaf). Active leaves available via currentStates.values() built at sm.ts:1540.
- _[medium]_ Backward-compat hazard from the proposed ancestor-matching change: switching from exact-regionKey lookup to 'fromState is ancestor of any active leaf' changes from-part matching from per-region-key to per-config-scan, which (1) loses the .every() guarantee that a multi-part from like 'a.x|b.y' matches ONLY when BOTH region keys are simultaneously in their stated leaves IF the new predicate is written as ANY-leaf — must preserve .every() over from-parts but make EACH part an ancestor-OR-equal test; (2) a bare 'parent' from would now ALSO match while the machine is in bare 'parent' (case 3) AND while expanded (cases 1/2), unifying the three entry behaviors — desirable, but it means a from:'parent' transition that authors previously assumed only fired in the bare state will now ALSO fire from any descendant leaf. Any author relying on bare-only matching (none in this repo, but possible externally) would see broadened eligibility. — isTransitionPossible .every() at sm.ts:1549; no repo test depends on bare composite-parent from (grep 'council'=none; robot/home joins use leaves per hierarchical.test.ts:348-349, coverage_boost.test.ts:1894 home is leaf).
- _[medium]_ Even after fixing isTransitionPossible matching, a from:'parent' transition's UML-join 'ALL regions final' intent is NOT expressible without an additional guard/final mechanism. The fix to matching alone yields ANY-leaf (parallel-exit) semantics. If the design intends true joins (fire only when every region is in its final substate), a separate feature is required (per-region final markers + an isInState-style In() guard, or an all-regions-final check in isTransitionPossible). This is a second, independent design decision beyond the matching fix. — No final-state/join gating in state_machine.ts; isInState/getCurrentStateInfo (sm.ts:579-613) expose regions/children but no 'final' concept.
- _[low]_ getRegionKey's lastIndexOf('.') design also means isTransitionPossible cannot today distinguish a parent 'p.region' from a leaf when the from has the same depth as the active leaf's region key — but this is incidental. The real fix should NOT touch getRegionKey (it is correct for parseCompositeState/updateState/removeConflictingStates region bookkeeping at sm.ts:1907,1937,1969,1999,2031); changing it would ripple into state-storage logic. Keep getRegionKey; change only the matching predicate in isTransitionPossible. — getRegionKey callers: sm.ts:586,1145,1165,1301,1553,1896,1907,1937,1969,1999,2031,2037 — most are storage/region-management, not matching.
