## Сначала — чего в списке НЕТ, и почему это важно

Четыре вещи я принял за ограничения библиотеки, и все четыре оказались моими
ошибками. Записываю их, чтобы план не чинил несуществующее.

| что я решил | как на самом деле | чем проверено |
|---|---|---|
| «`regions` принимает состояния, но не события» | переходы **адресуют вложенные пути**: `from: 'PHASE.gate.DA_PENDING'` работает | запуск: `PHASE.work.WORK_OPEN\|PHASE.gate.DA_PENDING` → … → `isDone: true` |
| «библиотека не поставляет `.d.ts`» | типы есть в `types/`, `exports` их отдаёт; я смотрел в `dist/` | `tsc --noEmit` на пробе — ноль ошибок |
| «джойн областей надо вешать гардом-замыканием» | есть декларативный `done.state.<id>`, движок поднимает его сам | запуск: через 20 мс состояние сменилось само |
| «`fireEvent` возвращает `void`, исходы неразличимы» | возвращает `Promise<boolean>`; бросок / `false` / `true` — три разных исхода | `state_machine.ts:452`; в его же JSDoc `const success = await sm.fireEvent(...)` |

Все четыре — про то, что я не прочитал возвращаемое значение, не поставил `await`
и смотрел не в тот каталог. **Ядро модели полное**: семантика машин менять не
требует. Дальше — про обнаружимость, два дефекта поведения и одну недостающую
операцию.

## Находки

Порядок — по цене последствий, а не по порядку обнаружения.

### F7 · Ошибка гарда неотличима от отказа гарда

Замер, один `fireEvent`:

| сценарий | возврат | бросок | состояние |
|---|---|---|---|
| гард вернул `false` | `false` | нет | прежнее |
| **гард бросил исключение** | **`false`** | **нет** | прежнее |
| нет подходящего перехода | — | `StateMachineError` | прежнее |
| гард вернул `true` | `true` | нет | новое |

Исключение проглатывается в `logger.error('Error determining allowed transition')`
(`state_machine.ts:388-396`) и наружу не выходит. В этой ветке **не вызывается**
`monitor.recordError` — он есть только в ветке `applyTransition`
(`state_machine.ts:424`). Упавший гард не попадает ни в возврат, ни в метрики,
только в лог.

**Цена.** Опечатка в гарде — обращение к полю `undefined`, неверное имя метода —
выглядит снаружи **ровно как легитимный отказ гейта**. Для MB3 это худший из
отказов: «DA не пропустил» и «гард гейта сломан» неразличимы, и второе не заметят.

*Найдено сопровождающим при ревью; подтверждено независимой пробой.*

### F8 · Гард победившего перехода исполняется ДВАЖДЫ за один `fireEvent`

Проба со счётчиком вызовов:

| конфигурация | вызовы гардов | итог |
|---|---|---|
| один переход, гард `true` | `g1,g1` | переход состоялся |
| один переход, гард `false` | `g1` | стоим |
| `canFireEvent` в одиночку | ноль | — |

Победивший гард зовётся дважды, отказавший — один раз, а `canFireEvent` не зовёт
вовсе (документация в этой части **точна**).

**Цена.** Контракт «гарды обязаны быть чистыми» **уже действует де-факто**, но
нигде не объявлен. Любой гард с побочным эффектом — счётчик итераций, запись в
лог, ленивая загрузка — срабатывает дважды на каждом успешном переходе.

### F9 · Побеждает ПОСЛЕДНИЙ подходящий переход, а не первый

Два перехода из одного состояния, один `fireEvent`:

| гарды | вызовы | итог |
|---|---|---|
| оба `true` | `g1,g2,g2` | **второй** |
| первый `true`, второй `false` | `g1,g2,g1` | первый |
| первый `false`, второй `true` | `g1,g2,g2` | второй |
| оба `false` | `g1,g2` | стоим |

Механизм — `getAllowedTransitions` (`state_machine.ts:1808`): есть поле
`transition.priority`, при отсутствии равное `-Infinity`. Условие пропуска
`priority < highestPriority`, то есть `-Infinity < -Infinity` ложно — перебираются
ВСЕ переходы, и каждый подошедший **перезаписывает** выбранный.

**Цена.** README заявляет соответствие SCXML/UML («Entry/exit follow SCXML/UML
ordering»), а там при равном приоритете выигрывает **первый в порядке
объявления**. Расхождение с заявленным стандартом. При этом само поле `priority`
(`types.ts:265`) — единственный способ управлять выбором — **не упомянуто ни в
README, ни в `docs/`**.

**Насколько опасно для MB3 сегодня:** не опасно, но по случайности. Во всех наших
машинах переходы из одного состояния защищены **взаимоисключающими** гардами
(`verdictApproves` / `verdictRejects`), поэтому кандидат всегда один. Это удача,
а не свойство конструкции.

### F2 · Нет способа вложить СУЩЕСТВУЮЩУЮ машину в область

`regions` принимает литерал состояний. Чтобы вложить готовый конфиг, нужно
вручную переписать `from`/`to` каждого перехода на путь
`<узел>.<область>.<состояние>`, проставить `final` и не забыть события. Я написал
это в потребителе — `buildHostedConfig`, около 120 строк работы с моделью, а не с
задачей.

**Чем это обошлось до меня.** В MB3 существовал `buildGatedPhaseRegions`, который
вместо вложения **скопировал** состояния машины критика руками. Замер копии
против оригинала:

```
состояние:  da-gate-sm → DA_APPROVED,  копия → DA_CLEARED   (имена разошлись)
события:    da-gate-sm → 6 штук,       копия → НОЛЬ
```

Копия потеряла процесс целиком: запустить через неё цикл ревью нельзя. Отсутствие
одной операции породило вторую, расходящуюся декларацию — ровно тот класс дефекта,
против которого машины и заводят.

### F1 · Джойн `done.state.<id>` срабатывает на ОТЛОЖЕННОМ тике

```
await sm.fireEvent('REVIEW_APPROVED')
sm.getCurrentState()        // PHASE.gate.DA_APPROVED  ← ещё не вышли
await new Promise(r => setTimeout(r, 20))
sm.getCurrentState()        // NEXT                    ← вышли
```

**Цена конкретная.** Я проверил состояние сразу после `await`, увидел старое,
заключил «декларативный джойн не работает» и написал обходной путь — фабрику с
гардом, замыкающим экземпляр машины. Лишний механизм из-за двадцати миллисекунд.

Флаш микрозадач в README **есть** — но в разделе про DST, применительно к
`invoke` (строка 124). В разделе «Hierarchical regions, parallel states & join»,
где это и кусается, про отложенность не сказано.

Показательно, что тот же обходной путь уже жил в MB3 до меня:
`gated-phase-composite.config.ts` вешает `guard: () => sm.isDone(P)` вместо
`done.state.<id>`. Два независимых потребителя пришли к одному обходу — значит
дело не в невнимательности.

### F3 · `canFireEvent` не исполняет гарды

В JSDoc сказано прямо («guards are not executed»), в README — нет. Имя читается
как «можно ли выстрелить», а отвечает «есть ли переход подходящей формы».

Я на этом ошибся в первой же пробе: `if (await sm.canFireEvent(ev))` дал `true`,
событие выстрелило, состояние не изменилось — в журнале это выглядело как
«переход состоялся в то же состояние».

**Важно:** «узнать заранее, пропустит ли гард» — вопрос, на который в асинхронной
очереди корректного ответа нет (см. ниже про TOCTOU). Закрывается он не новым
методом, а разбором результата выстрела.

### F5 · `fireEvent` асинхронный, но Quick start об этом молчит

В примере Quick start `fireEvent` не вызывается вовсе. Следствие в поле:
эталонный тест потребителя (`sm-lock.test.ts` в MB3) вызывает `sm.fireEvent('EXPIRE')`
**без `await`** и проходит по совпадению — переходы успевают примениться, пока
цепочка короткая.

### F6 · Типы лежат в `types/`, а `dist/` без `.d.ts`

`exports` настроен корректно, `tsc` их находит. Но беглый осмотр `dist/` создаёт
впечатление, что типов нет: я на этом основании насыпал `any` в тестах
потребителя. Дефекта в пакете нет — есть ловушка первого впечатления.

## План

Порядок — по отношению пользы к цене. Первые четыре шага целиком
документационные, и вместе они закрывают **все** ошибки из первого раздела.

### 1. Отложенность джойна — в раздел про регионы  *(закрывает F1)*

Абзац и пример с флашем прямо в «Hierarchical regions, parallel states & join».
Сейчас про микрозадачи сказано только в DST-разделе про `invoke`.

Дешёвое усиление: у примера с `guard: () => sm.isDone('proc')` дописать, что это
**синхронная альтернатива** отложенному `done.state`, а не просто второй стиль.

*Цена:* минимальная. *Польза:* самая дорогая ошибка на самую дешёвую правку; два
независимых потребителя уже построили обход.

### 2. `await` в Quick start + строка про асинхронность  *(закрывает F5)*

Одна правка примера, одна фраза.

### 3. Типы: реэкспорт `dist/index.d.ts` либо строка в README  *(закрывает F6)*

Дефекта нет — чинится ловушка первого впечатления.

### 4. `canFireEvent`: перенести «guards are not executed» в README  *(закрывает F3)*

И назвать честный сценарий применения — построение меню доступных действий, где
гонка не важна (меню и так перерисовывается).

**Пункт «`canFireEventNow` с исполнением гардов» снят** — по трём измеренным
причинам, каждая самостоятельна:

- **TOCTOU.** Сразу после `fireEvent('go')`, когда событие уже в очереди, но не
  обработано, `canFireEvent('go')` всё ещё отвечает `true` — хотя второй выстрел
  уже обречён. Исполнение гардов гонку не чинит, только удорожает ответ.
- **Побочные эффекты.** Пара «проверил + выстрелил» вызовет гард ещё раз — а он и
  так зовётся дважды (F8).
- **Сигнатуры расходятся.** У `canFireEvent` второй параметр — `adaptee`, а гарду
  нужен `...args` события. Два соседних метода, различающихся одной буквой и
  несовместимых по второму параметру, — ловушка ровно того класса, против
  которого написан весь документ.

Потребность «узнать, пропустит ли гард» закрывается шагом 6: единственный
корректный ответ даёт сама попытка выстрела.

### 5. `priority` и порядок выбора перехода  *(закрывает F9)*

Развилка, и она за сопровождающим:

- **либо** задокументировать как есть — «при равном приоритете побеждает
  последний объявленный» — и описать поле `priority` в README;
- **либо** привести к SCXML/UML («первый в порядке объявления») — это ломающее
  изменение поведения, требующее мажора и миграционной заметки.

Второе честнее относительно заявленного соответствия стандарту, но дороже.
В любом случае `priority` обязан появиться в документации: сейчас единственный
рычаг управления выбором не описан нигде.

### 6. Ошибка гарда: `reason: 'guard-error'` + `recordError`  *(закрывает F7)*

Прокинуть в монитор `recordError` из ветки `getAllowedTransitions` и различить
исход в детальном результате (шаг 7). Сломанный гард обязан быть отличим от
сработавшего.

*Польза:* опаснее прочего по последствиям, дешевле пунктов 7 и 8 по цене.

### 7. `fireEventDetailed()` → `FireResult`  *(аддитивно)*

```ts
type FireResult = {
  fired: boolean
  reason?: 'no-transition' | 'guard-rejected' | 'guard-error'
  transition?: string        // 'A -> B'; имена гардов почти всегда анонимны
  error?: Error              // для 'guard-error'
}
```

**Возврат `fireEvent` НЕ меняется.** Предложенный в первой редакции
`{ fired: false }` — truthy объект: любой `if (await sm.fireEvent(e))` молча
инвертировался бы, и TypeScript этого не поймал бы. Плюс `fireEvent` — метод
`@stable` символа, смена возврата по собственной STABILITY.md мажорна.

### 8. Двойное исполнение гарда  *(закрывает F8)*

Либо убрать повторный вызов победившего гарда, либо объявить контракт чистоты
явно в документации. Первое предпочтительнее: контракт, о котором никто не знал,
уже нарушается существующими гардами.

### 9. `composeIntoRegion(host, node, region, guest, opts)`  *(закрывает F2)*

Публичная операция: взять конфиг гостя, положить его состояния в область узла
хозяина, переписать пути переходов, проставить `final` на состояниях выхода.

Проверки внутри — каждая закрывает свой способ получить молча неработающий
результат:

- узла нет у хозяина → отказ, а не тихое добавление недостижимой ветки;
- список финальных пуст или называет несуществующее состояние → отказ: без
  финальных листьев `isDone` не сомкнётся никогда, и узел станет ловушкой;
- коллизия имён областей в одном узле → отказ.

*Критерий приёмки:* потребитель удаляет свой `buildHostedConfig` и
`buildGatedPhaseRegions`, а тесты цикла ревью (отправка → отказ → доработка →
возврат → приёмка) остаются зелёными.

*Цена:* средняя — логика написана и обкатана у потребителя, переносится с
тестами. Последняя в списке не по важности, а потому что документация и два
дефекта поведения дешевле и срочнее.

## Чего этот план сознательно НЕ трогает

**Семантику модели.** Иерархия, ортогональные области, порядок входа-выхода,

штатная процедура.

**Производительность.** Не измерял — утверждать нечего.

# Ревью пунктов 3 и 4 — со стороны сопровождающего

> Добавлено 2026-07-28. Тот же стандарт доказательности: каждое утверждение ниже

## Замер, на который опирается всё дальнейшее

Машина `A --go--> B` с гардом, событие `other` объявлено только из `B`:

| сценарий | `await fireEvent(...)` | бросок | состояние |
|---|---|---|---|
| гард вернул `false` | `false` | нет | `A` |
| **гард бросил исключение** | **`false`** | **нет** | `A` |
| нет подходящего перехода (`other` из `A`) | — | `StateMachineError: Invalid event: other for state: A` | `A` |
| гард вернул `true` | `true` | нет | `B` |

Плюс отдельный замер очереди:

```
canFireEvent('go') до fireEvent                      → true
canFireEvent('go') сразу после fireEvent (в очереди) → true    ← событие ещё НЕ обработано
canFireEvent('go') после await                       → false   ← состояние B
```

## В1 · Формулировка F4 фактически неверна: различение уже есть

F4 утверждает: «неуспешный гард → молчаливый no-op… вызывающий не может их
различить, не сравнивая состояние до и после». Замер показывает три разных
исхода: **бросок** (нет перехода по форме), **`false`** (гард не пропустил),
**`true`** (переход применён). `fireEvent` возвращает `Promise<boolean>` с
самого начала — `state_machine.ts:452`, `types/state_machine.d.ts:70`,
`etc/statemachine.api.md:488`, JSDoc: «True if a transition occurred».

Отсюда и правка к тексту пункта 3: «`fireEvent` возвращает не `void`» — неточно,
он возвращает `Promise<boolean>`. Наблюдение «неразличимо» возникло по той же
причине, что и F5: возвращаемое значение не читалось, как и `await` не ставился.
Это **та же ловушка обнаружимости**, что F3/F5/F6, и лечится она в первую очередь
строкой в README, а не сменой сигнатуры.

## В2 · Настоящий дефект рядом: ошибка гарда неотличима от отказа гарда — F7

Строка 2 замера: гард, бросивший исключение, даёт `fireEvent → false` **без
броска**. Исключение проглатывается в `logger.error('Error determining allowed
transition')` (`state_machine.ts:388-396`) и наружу не выходит.

Цена выше, чем у исходного F4: опечатка в гарде (обращение к полю `undefined`,
неверное имя метода) выглядит снаружи **ровно как легитимный отказ гейта**. Для
MB3 это худший из возможных отказов: «DA не пропустил» и «гард гейта сломан»
неразличимы, и второе не заметят.

Хуже того, в этой ветке не вызывается `monitor.recordError` — он есть только в
ветке `applyTransition` (`state_machine.ts:424`). То есть упавший гард не попадает
даже в метрики: ни в возврат, ни в монитор, только в лог.

**Предложение:** завести это как отдельную находку F7 и поставить её выше
пунктов 3 и 4. Она дешевле их обоих (различить `reason: 'guard-error'` и прокинуть
`recordError`) и опаснее по последствиям.

## В3 · Возражение по существу к пункту 3: предложенная замена ломает тихо

`{ fired: false, reason: 'guard-rejected' }` — **truthy объект**. Любой код вида

```ts
if (await sm.fireEvent('APPROVE')) { /* прошло */ }
```

инвертируется молча: раньше ветка не выполнялась при отказе гарда, теперь
выполняется всегда. TypeScript этого не поймает — `if (obj)` типизируется.

Оговорка документа («существующий код, игнорирующий результат, продолжает
работать») верна, но защищает не тех: страдает как раз код, который результат
**использует**. Внутри библиотеки контракт закреплён тестами
(`basic.test.ts:138,263`, `edge_cases.test.ts:60`, `coverage_boost.test.ts:845` и
далее — `resolves.toBe(true|false)`), они сломаются шумно и это хорошо. У внешнего
потребителя такой сети нет.

Плюс формальная сторона: `fireEvent` — метод `@stable` символа `StateMachine`
(STABILITY.md, «5 firm symbols»). Смена возвращаемого типа — по собственной
политике пакета **мажорный** бамп, а не «минимальный вариант, ничего не ломающий».

**Предложение — аддитивный метод-сосед вместо смены возврата:**

```ts
type FireResult = {
  fired: boolean
  reason?: 'applied' | 'no-transition' | 'guard-rejected' | 'guard-error'
  transition?: string   // 'A -> B' — движок уже формирует это в ErrorContext
  error?: Error         // заполняется при 'guard-error' (закрывает В2/F7)
}

fireEventDetailed(event, ...args): Promise<FireResult>
```

`fireEvent` остаётся как есть и выражается через новый метод. Новый символ
рождается `@unstable` → минорный релиз, снимок `etc/statemachine.api.md`
обновляется штатной процедурой, ратчет-тест `public_surface.test.ts` — тоже.

Отдельно про `guard?: string` из исходного предложения: в реальных конфигах гарды
почти всегда анонимные стрелки (`guard: () => sm.isDone('proc')` — прямо из
README:78), и движок в контексте ошибки пишет `action: "anonymous"`. Поле будет
пустым в самом частом случае. Полезнее `transition: 'A -> B'` — движок уже
собирает эту строку (`state_machine.ts:1826`) и она идентифицирует переход
однозначно.

Про альтернативу с событием монитора `guard_rejected`: как **дополнение** — да,
для потоковой диагностики. Как **замена** — нет: монитор глобален по машине, а
гейту нужен ответ по конкретному вызову; при двух параллельных `fireEvent`
корреляции «какое событие отклонил гард» не будет.

## В4 · Возражение к пункту 4: `canFireEventNow` даёт ложную гарантию

`canFireEvent` читает **текущее** состояние, а `fireEvent` кладёт событие в
очередь (`enqueueEvent` → `queueMicrotask`, `state_machine.ts:222-289`).
Второй замер: сразу после `fireEvent('go')` — когда событие уже в очереди, но не
обработано — `canFireEvent('go')` всё ещё отвечает `true`, хотя второй
`fireEvent('go')` в этот момент уже обречён на `Invalid event`.

Исполнение гардов внутри проверки эту гонку **не чинит, а удорожает**: ответ
становится дороже и всё так же успевает устареть между проверкой и выстрелом.
Классический check-then-act поверх асинхронной очереди.

Для гейта — сценария, ради которого пункт и заведён — корректный паттерн
единственный: **выстрелить и разобрать результат**, то есть пункт 3, а не 4.

## В5 · Исполнение гардов «на пробу» небезопасно по побочным эффектам

Гард — произвольная async-функция, получающая adaptee и context; чистоты от неё
никто не требует и обеспечить её нечем. Пара `canFireEventNow(...)` + `fireEvent(...)`
вызовет гард **дважды**. Значит новый метод вводит задним числом контракт «ваши
гарды обязаны быть чистыми» — на уже написанные гарды, которые под него не
писались.

## В6 · Сигнатура не сходится: гард принимает `...args`

`getAllowedTransitions(obj, transitions, ...args)` (`state_machine.ts:1808`)
передаёт гарду payload события. Чтобы проверить гард **честно**, `canFireEventNow`
обязан принять тот же payload:

```ts
canFireEvent(event, adaptee?): boolean            // второй параметр — adaptee
canFireEventNow(event, ...args): Promise<boolean> // второй параметр — payload
```

Два соседних метода, различающиеся одной буквой в имени и **несовместимые по
второму позиционному параметру** — ловушка обнаружимости ровно того класса,
против которого написан весь этот документ. Без `args` метод проверяет не то
событие, которое выстрелит; с `args` — расходится с соседом.

Дополнительно: `getAvailableEvents()` построен на `canFireEvent`
(`state_machine.ts:553`). Появление «Now»-варианта немедленно порождает вопрос
о `getAvailableEventsNow()` — а там прогон **всех** гардов подряд с побочными
эффектами уже недопустим прямо.

## Предложение по пункту 4: понизить до документации

F3 — находка про **обнаружимость**, и закрывать её надо документацией: перенести
JSDoc-строку «guards are not executed» в README рядом с методом и назвать честный
сценарий применения — построение меню доступных действий (для чего метод и
годится, гонка там не важна: меню и так перерисовывается).

Потребность «узнать, пропустит ли гард» закрывается пунктом 3 —
`fireEventDetailed`, — потому что единственный корректный ответ на этот вопрос
даёт сама попытка выстрела.

Если метод всё же нужен (UI-превью, где выстрелить нельзя) — то не `Now` в имени:
«Now» читается как про время, а не про исполнение гардов. Тогда `evaluateEvent(event, ...args)`
с явным JSDoc про двойное исполнение гарда и про TOCTOU.
