# MASTER-план: ремедиация `@vedmalex/statemachine` + фасад `checkMachine`

> Управляющий план. Дизайн API `checkMachine`, полный реестр найденных дефектов с критериями
> подтверждения, волны исполнения, процесс. Детали семантики — в `SPEC-selection-and-microstep.md`;
> здесь — программа и процесс.
>
> Черновик 2026-07-28. Статус: **на проверке критиком** (mb3-critic, advisory, вне mb3-гейтов).

## 0. Принципы

1. **Доверенный вердикт — цель всего.** Библиотека и её симулятор ценны ровно настолько, насколько
   их «зелёному» можно верить. Каждый дефект класса «молча врёт» (RCE, fail-open, false-negative,
   проглоченная ошибка) приоритетнее любого удобства.
2. **Каждый фикс подтверждается воспроизведением.** Правило: сначала тест, КРАСНЕЮЩИЙ на текущем
   баге (red-test), затем фикс, затем тот же тест зелёный + независимая адверсариальная верификация.
   Фикс без красневшего-до теста не принимается — иначе неизвестно, что он вообще что-то чинит.
3. **Ничего не оставляем «на потом».** Все находки — в реестре §6 со статусом; закрытие только через
   протокол §4.
4. **Работа через workflows**, агенты по задаче (роутинг §5). Оркестратор проверяет диффы и teeth
   субагентов — зелёный отчёт необходим, но не достаточен.
5. **Стабильность поверхности НЕ ограничивает (директива владельца 2026-07-28).** Ломающие
   изменения свободны; `@stable`/`STABILITY.md`/semver-мажоры/обратная совместимость персистентных
   данных — НЕ сдерживающий фактор. Приоритет — эффективность и корректность вердикта. Обновление
   `etc/*.api.md` остаётся (машинно-проверяемая поверхность), но как факт, а не как гейт. Это НЕ
   ослабляет корректность/доверие/red→green — они про правильность, а не про стабильность.
6. **Только полнота — никаких уменьшений (директива владельца 2026-07-28).** По ходу исполнения
   допускаются ТОЛЬКО улучшения и расширения: если вскрывается новый дефект/случай/проверка — она
   ДОБАВЛЯЕТСЯ в scope. Сокращать, упрощать в ущерб, выкидывать пункты реестра §6 — НЕЛЬЗЯ. Scope
   монотонно растёт или уточняется вверх. «Слишком дорого/долго» не основание урезать — основание
   разбить на под-волны, но выполнить целиком.
7. **План-факт по факту КАЖДОЙ волны (директива владельца 2026-07-28).** После завершения волны —
   обязательный артефакт `.plan/fact/W<N>-plan-vs-fact.md`: что планировалось (реестр §6 + критерии),
   что сделано фактически, дельта, вскрытые новые дефекты (→ в реестр по §0.6), подтверждения
   red→green по каждому id. Волна не считается закрытой без этого артефакта.

## 1. Процесс исполнения (петля)

```
        ┌─────────────────────────────────────────────────────────┐
        ▼                                                         │
  [ПЛАН волны] → [mb3-critic: проверка плана] → PROCEED?          │
        │ REVISE                                     │ да          │
        └────────────────────────────────────────────┘            │
                                                     ▼            │
                          [WORKFLOW: выполнение волны]             │
                                     ▼                             │
                          [ВАЛИДАЦИЯ: red→green + adversarial-verify]
                                     ▼                             │
                             докрутили? ── нет ──► [ПРАВКИ] ───────┘
                                     │ да
                                     ▼
                          [mb3-critic: приёмка волны] → следующая волна
```

- **Проверка плана и приёмка** — `Agent(subagent_type="mb3-critic")`, advisory (CAR: Challenge /
  Alternative / Risk). НЕ mb3-workflow: не заводим mb3-задачу, не эмитим фазовые гейты; критик
  возвращает разбор прозой, его вердикт — вход для решения оркестратора, не runtime-гейт.
- **Выполнение** — Workflow: fan-out edit-агентов по непересекающимся файлам, затем verify-стадия.
- **Валидация** — отдельный workflow: по каждому дефекту прогон red-test (должен был краснеть до
  фикса — проверяется на предыдущем коммите), затем зелёный после, затем adversarial-verify
  (независимый агент пытается ОПРОВЕРГНУТЬ, что баг закрыт).
- **Правки** — если валидация нашла недокрутку, правочный workflow; цикл не закрывается, пока
  красное не станет зелёным.

## 2. Дизайн API `checkMachine`

Потребитель отдаёт свою машину и алфавит событий → получает доверенный отчёт. Контракт спроектирован
так, чтобы аудит-находки sim были **невыразимы**: `ok:true` при нуле оракулов невозможен,
liveness в headline, escape — предупреждением.

### 2.1 Сигнатура

```ts
// @stable — публичная поверхность фасада
export async function checkMachine<T extends object>(
  config: StateMachineConfig<T>,
  owner: OwnerSource<T>,
  options?: CheckOptions<T>,
): Promise<CheckReport>

/** Один живой owner на 32 прогона ломает независимость прогонов и детерминизм seed
 *  (прогон N мутирует owner для N+1). При runs>1 фабрика ОБЯЗАТЕЛЬНА — иначе бросок.
 *  Регресс относительно самого субстрата: runSimulation уже принимает фабрику (public.ts:96). */
export type OwnerSource<T extends object> =
  | T | Adapter<T>                        // допустимо только при runs===1
  | ((env: SimEnv) => T | Adapter<T>)     // требуется при runs>1
```

### 2.2 Опции

```ts
export interface CheckOptions<T extends object> {
  /** Алфавит фаззинга. По умолчанию — ВСЕ события config.events без payload.
   *  Если у события есть аргументы — потребитель ОБЯЗАН задать payload, иначе
   *  в warnings попадёт "событие E фаззится без payload — ветви по args не покрыты". */
  events?: EventSpec[]

  /** Детерминизм: тот же seed → тот же отчёт. Строка-число или bigint. */
  seed?: string | bigint

  /** Бюджет одного прогона (число событий) и число независимых прогонов (сидов). */
  steps?: number          // по умолчанию 1000
  runs?: number           // по умолчанию 32

  /** Инварианты потребителя поверх встроенных. */
  invariants?: MachineInvariant<T>[]

  /** Встроенные проверки. По умолчанию 'all-working' — только РАБОЧИЕ после починки sim,
   *  мёртвые I-4/I-5/I-9 сюда не входят, пока не реализованы (анти-A3: не рекламируем
   *  покрытие, которого нет). */
  builtins?: BuiltinCheck[] | 'all-working'

  /** safety | liveness | both. По умолчанию 'both' — liveness в headline (анти-A4). */
  mode?: 'safety' | 'liveness' | 'both'

  /** Что переводит ok в false. По умолчанию STRICT для CI: ВСЕ FailCause.
   *  degradation = непустые warnings (анти-A2: деградация, ушедшая в warnings, при 'warn'
   *  оставляла бы ok:true — «потребитель обязан прочитать warnings» есть тот самый социальный
   *  контракт, отказ которого породил A2; в CI читают одно поле — ok). */
  failOn?: FailCause[]

  /** Точечное ослабление degradation по ВИДУ warning — вместо капитуляции всего класса.
   *  Мотив: событие-без-payload будет на КАЖДОЙ MB3-машине до написания генераторов; без
   *  гранулярности единственный рычаг — выкинуть 'degradation' целиком, т.е. вернуть A2 одним
   *  движением. degradationExcept гасит шум точечно, строгость на остальном сохраняется. */
  degradationExcept?: WarningKind[]

  /** Escape реальных таймеров (анти-A5). По умолчанию 'warn' → warning kind 'timer-escape' →
   *  FailCause 'escape'. */
  onRealTimerEscape?: 'warn' | 'fail' | 'ignore'
}
export type FailCause =
  | 'violation' | 'deadlock' | 'non-converging'   // висящий лэйн — структурная находка уровня deadlock
  | 'no-progress' | 'livelock' | 'escape' | 'degradation'

export interface EventSpec<T extends object> {
  name: string
  /** Детерминированный генератор аргументов; ВИДИТ снимок текущей конфигурации.
   *  Без snapshot фаззер слеп к состоянию: реальные события MB3 — verdict-объекты,
   *  осмысленные лишь относительно текущего гейта; генератор без снимка выдаст мусор,
   *  гарды отсекут всё, покрытие схлопнется. Это единственная точка, где генерация
   *  видит состояние — иначе фасад бесполезен на машинах его единственного потребителя. */
  payload?: (rng: Rng, snapshot: MachineSnapshot<T>) => unknown[]
  /** Относительный вес в фаззинге (по умолчанию 1). */
  weight?: number
}

export interface MachineInvariant<T extends object> {
  name: string
  /** Предикат над снимком после каждого шага. false ИЛИ бросок → нарушение.
   *  Бросок внутри инварианта — тоже нарушение (не проглатывается — анти-F7). */
  check: (snapshot: MachineSnapshot<T>) => boolean
}
```

### 2.3 Отчёт

```ts
export interface CheckReport<T extends object> {
  ok: boolean

  /** Два инварианта контракта, оба проверяются тестом (анти-A2 + анти-вакуумный-оракул):
   *   ok===true ⇒ oraclesRun>0        — не бывает зелёного без единого оракула;
   *   ok===true ⇒ transitionsFired>0  — не бывает зелёного над НЕПОДВИЖНОЙ машиной
   *     (мёртвый алфавит / гарды, режущие всё → машина не покидает initial, оракулы
   *      крутятся над точкой, ok:true — вакуумный обход oraclesRun>0). */
  oraclesRun: number
  transitionsFired: number

  seed: string            // канонический, для воспроизведения
  runs: number
  steps: number

  // ── Покрытие (побочный продукт нормализованной модели, §SPEC 1) ──
  reachableStates: string[]
  unreachableStates: string[]                                   // объявлены, не посещены
  uncoveredTransitions: Array<{ event: string; from: string; to: string }>
  deadEvents: string[]                                          // ни одного срабатывания
  /** Покрытие ГАРДОВ — какой ни разу не вернул true / ни разу false. Прямо отвечает
   *  требованию §SPEC 13.1 «data-dependent guard coverage», без него «что чинить» слепо. */
  guardOutcomes: Array<{ transition: string; sawTrue: boolean; sawFalse: boolean }>

  /** Снимок конфигурации + данных adaptee, видимый payload-генератору и инвариантам.
   *  ВКЛЮЧАЕТ данные owner/adaptee (не только имена состояний) — иначе payload не сгенерит
   *  stateful-событие MB3 (verdict для текущего гейта), а инвариант не проверит данные. */
  // type MachineSnapshot<T> = { config: string /* '|'-нормализ. */; state: string;
  //   data: Readonly<T>; queueDepth: number; pendingTimers: number }
  /** Насыщение покрытия по прогонам — растёт ли ещё или вышло на плато. Без этого
   *  открытый вопрос «хватает ли runs:32/steps:1000» нерешаем в принципе. */
  saturation: { plateauedAtRun: number | null; newCoveragePerRun: number[] }

  // ── Структурные находки ──
  deadlocks: Array<{ state: string; trace: EventTrace }>        // конфигурация без исходящих
  nonConvergingRegions: Array<{ composite: string; region: string; trace: EventTrace }>
  livelocks: Array<{ reason: string; trace: EventTrace }>       // неквиесценция/run-away (анти-A4)

  // ── Нарушения ──
  violations: Array<{
    invariant: string
    /** 'engine' — синтетика движка (unhandledRejection, A1): НЕ нарушение модели потребителя,
     *  чинит РАЗРАБОТЧИК ДВИЖКА, не автор машины. 'builtin'/'user' — про машину потребителя. */
    kind: 'engine' | 'builtin' | 'user'
    witness: string
    minimalTrace: EventTrace        // зашринкованный; fingerprint сохранён (проверяется round-trip)
    /** Сниппет ОТНОСИТЕЛЬНО фабрики owner потребителя (sim не знает конструктора живого
     *  owner — «самодостаточный» было недостижимым обещанием). */
    reproCode: string
  }>

  /** Честные границы прогона — при STRICT failOn непустой массив делает ok:false, а не
   *  полагается на то, что потребитель их прочтёт (это и был провал A2). Напр.:
   *  "событие E без payload — ветви по args не покрыты", "escape реального таймера в S". */
  warnings: string[]
}
```

**Таблица предиката `ok`** (§CAR-1: без неё контракт fail-open по построению — перечислены поля,
но не сказано, что валит вердикт). При дефолтном STRICT `failOn`:

| условие | вклад в `ok:false` | причина |
|---|---|---|
| `violations` непуст (kind builtin/user) | да ('violation') | нарушение модели |
| `violations` (kind engine) | да, отдельным сигналом | баг движка, не машины — маршрутизируется разработчику движка |
| `deadlocks` непуст | да ('deadlock') | тупик почти всегда дефект |
| `nonConvergingRegions` непуст | **да ('non-converging')** | висящий лэйн — структурная находка уровня deadlock; без этой строки машина с вечным лэйном прошла бы `ok:true` |
| `livelocks` непуст | да ('livelock') | неквиесценция/run-away |
| `transitionsFired===0` | да ('no-progress') | полностью неподвижная машина |
| `deadEvents` непуст ПРИ достигнутом плато `saturation` | да ('degradation' warning) | вакуумность-по-частям: машина дёргается по 1 мусорной ветке, 95% алфавита мёртво — плато доказывает, что это не «ещё не дошли» |
| `uncoveredTransitions` непуст ПРИ плато | да ('degradation' warning) | то же — исчерпанное покрытие с дырами = дефект алфавита или машины |
| `oraclesRun===0` | да (жёстко, не отключается) | нечего было проверять |
| `warnings` непуст | да ('degradation', гранулярно через `degradationExcept`) | деградация не должна тихо зеленеть |
| `unreachableStates` непуст | НЕТ (репортится) | может быть намеренно (dead-by-design) |
| `uncoveredTransitions` до плато | НЕТ (репортится) | покрытие ещё растёт — `saturation` покажет, дошло ли до плато |

`deadEvents`/`uncoveredTransitions` завязаны на `saturation`: до плато — репорт, на плато — degradation
(закрывает «машина двигается, но по мусорным веткам» тем же контуром, без произвольного порога «доля
живых событий»). Потребитель ослабляет через `failOn`/`degradationExcept` осознанно; дефолт строгий.

**Тип warnings** (гранулярность против alert-fatigue): `Array<{ kind: WarningKind; detail: string }>`,
`WarningKind = 'no-payload' | 'timer-escape' | 'dead-events-at-plateau' | 'uncovered-at-plateau' | …`.

### 2.4 Семантика, кодирующая анти-находки

| находка | как контракт делает её невыразимой |
|---|---|
| A2 fail-open | `oraclesRun` И `transitionsFired` в отчёте; `ok:true ⇒ oraclesRun>0 ∧ transitionsFired>0`; STRICT `failOn`; дефолт `builtins:'all-working'` |
| вакуумный оракул | `transitionsFired>0` — зелёное над неподвижной машиной невозможно |
| деградация-в-warnings | `failOn` включает `'degradation'`: непустые warnings → `ok:false` (не соц. контракт «прочти warnings») |
| A4 liveness | `livelocks` в headline; `mode` по умолчанию `both` |
| A5 escape | escape → `warnings` → при STRICT `failOn` валит `ok` |
| A3 фейк-покрытие | `builtins:'all-working'` НЕ включает нереализованные I-4/I-5/I-9; meta-тест реестра (§4а) гарантирует, что каждый заявленный builtin умеет стрелять |
| F7 ошибка гарда/инварианта | бросок в `MachineInvariant.check` — нарушение, не проглатывание |
| слепота к состоянию | `payload(rng, snapshot)` видит конфигурацию; фабрика owner при `runs>1` держит детерминизм |
| shrinker теряет баг | `minimalTrace` обязан сохранять `fingerprint` — round-trip тест |
| engine-баг ≠ баг машины | `violations[].kind:'engine'` маршрутизирует синтетику движка (A1) отдельно |

## 3. Волны исполнения

Порядок — по зависимостям и цене доверия. Каждая волна проходит петлю §1.

Правки после ревью критика: W5 **расщеплён** (сантехника sim не зависит от семантики — идёт
параллельно W2–W3; семантика sim зависит от нового тайминга `done.state` — после W3); #10 вынесен из
мега-волны W3 в **W3b** (это новая фича, не ремедиация; связь с W3 только по файлам); **D2 поднят
рано** — даёт DST-сеть безопасности ПОД самой рискованной W3 (и требование CD-63); red-test'ы
sim-блокеров **снимаются до W1** (см. §4б — фикс П2 уничтожает воспроизведение A1).

## 4. Протокол подтверждения исправления (для КАЖДОГО дефекта)

1. **Red-test.** Написать тест, воспроизводящий дефект, и убедиться, что он **краснеет на текущем
   HEAD** (до фикса). Без этого шага фикс не начинается — красное-до доказывает, что тест ловит
   именно этот баг.
2. **Fix.** Правка через edit-агента (роутинг §5).
3. **Green.** Тот же тест зелёный после фикса. Полный прогон сьюта — без новых красных.
4. **Adversarial-verify.** Независимый агент (verify-стадия workflow) пытается ОПРОВЕРГНУТЬ, что баг
   закрыт: строит вариацию сценария, обходной вход, граничный случай. Если воспроизводит остаток —
   дефект НЕ закрыт, возврат к §4.2.
5. **Critic-приёмка волны.** `mb3-critic` (advisory) по диффу волны: не появилось ли регрессий, не
   ослаблены ли тесты ради зелёного, честны ли red→green переходы.
6. **Реестр.** Статус в §6 → `закрыт`, с ссылкой на red-test и verify.

Анти-паттерн, который критик обязан ловить: тест, зелёный и до, и после (ничего не проверяет);
ослабленный ассерт; удалённый тест вместо починки; `/* c8 ignore */` вместо разбора недостижимости;
**red по неправильной причине** (тест падает на постороннем крэше, а не на ожидаемом ассерте) — red
обязан падать на ОЖИДАЕМОМ ассерте, проверяется по сообщению/типу падения. Критик приёмки проверяет
наличие red-артефакта на КАЖДЫЙ id реестра §6, а не «на волну целиком».

### 4а. Self-test оракулов (обязателен для всех builtin sim)

Свежереализованные I-5/I-9 и починенный I-3 — новый код, на котором стоит вердикт `checkMachine`.
Их собственный red-test доказывает лишь «стреляет на одном свидетеле». Три уровня доверия:

1. **Meta-тест реестра оракулов.** Для КАЖДОГО заявленного builtin существует фикстура-нарушитель,
   на которой он ОБЯЗАН эмитить Violation. Этот тест краснеет СЕГОДНЯ на I-4/I-5/I-9 (не могут
   стрелять), зеленеет и при реализации, И при честном удалении из реестра — это и есть red-test для
   «находок-удаления» (I-4), где обычный red невозможен.
2. **Нулевой-ложняк-корпус.** Все builtins прогоняются по корпусу заведомо КОРРЕКТНЫХ машин (тот же
   корпус MB3, §6а — двойная окупаемость): ноль violation. Это критерий закрытия A3/C1 (C1 —
   уже случившийся ложняк, прецедент).
3. **Дифференциальная проверка** где возможно: I-5 «полностью финален» против независимого
   вычисления по модели компилятора W2 (две реализации из разных кодовых путей; расхождение = флаг).

### 4б. Спец-режимы red (классы, где «red→green» не работает напрямую)

- **Перф (П14)** — порог по времени флейкает на CI-железе. Red = **счётная проба**: инструментировать
  горячий путь счётчиком (число обходов регионов на `setCurrentState` при R=320), ассертить O(R), не
  миллисекунды. Детерминированно везде.
- **Находки-удаления (I-4, legacy-функции П1)** — red через meta-тест реестра (§4а.1), а не прямой.
- **Семантика (F9/OTS)** — red-test подтверждает соответствие SPEC, но НЕ правильность самой SPEC
  (§SPEC 4/6.2 — авторская реконструкция SCXML, не дословный стандарт; adversarial-verify слеп, у
  него тот же оракул — та же SPEC). Независимая опора — **внешние conformance-векторы** (W3C SCXML
  IRP, применимые к пересечению семантик): §4в.
- **red-тесты sim-блокеров снимаются в W1 и замораживаются.** Причина: фикс П2 (W1, catch во
  внутренней ветке) уничтожает воспроизведение A1 — `unhandledRejection` перестаёт возникать, и
  после W1 red-test A1 «на текущем HEAD» физически не покраснеет. Аудит их уже прогонял — дёшево
  снять сейчас, применять в W5a.

### 4в. Внешние conformance-векторы (семантика W3)

Для правила селекции и OTS — не только собственные тесты, но и подмножество W3C SCXML IRP-тестов,
применимых к пересечению семантик библиотеки и стандарта. Ловит класс «SPEC внутренне
непротиворечива, но расходится со стандартом» — который adversarial-verify по построению не видит.
Границы применимости (`priority` — расширение, single-transition vs OTS) документируются: какие
IRP-векторы применимы, какие намеренно нет.

## 7. Открытые вопросы — РЕШЕНЫ (после ревью критика)

- **Волновой порядок:** W5 расщеплён — сантехника (W5a) параллельно W2–W3, семантика (W5b) после W3.
  РЕШЕНО в §3.
- **Характеризация vs целевые SCXML-red:** «и-и», не «или». Характеризация — датчик для W2 (у
  существующих тестов нулевая чувствительность к селекции); целевые SCXML-red — финишная черта W3;
  каждый характеризационный тест в W3 переписывается в парный целевой = скелет migration-note.
  РЕШЕНО в §3/§4в.
- **Перф-red:** счётная проба (итерации, не миллисекунды). РЕШЕНО в §4б.
- **Бюджет `runs:32/steps:1000`:** решается данными — поле `saturation` в отчёте (§2.3) показывает
  плато покрытия; ранний выход при насыщении. РЕШЕНО в API.
- **`transitionTimeout` при нескольких переходах за микрошаг (SPEC §11):** ДОЛЖЕН быть закрыт ДО W3
  (гейт волны §3). **Владелец гейта: задача первого шага W3** — до реализации OTS оркестратор
  принимает решение (один дедлайн на микрошаг vs на переход) и вписывает в SPEC §6. Гейт без
  назначенного владельца = гейт, о который W3 споткнётся в последний момент.
- **Прочие два вопроса SPEC §11 (multi-part `from`, кросс-региональный конфликт)** фактически решены
  текстом самой SPEC («спека сохраняет», «спека выбирает первое») — SPEC §11 привести в соответствие:
  пометить решёнными, не числить открытыми.
